**Owner:** Džiugas

plan for a product, not a demo.

## Definition of parity

Parity is not a feeling. It is six checkable statements:

1. **Coverage.** Every in-force e-TAR act is searchable; LITEKO court decisions
   are searchable; at least six institution-explanation sources are ingested;
   Seimas drafts and committee transcripts are ingested; EU law and ECHR are
   ingested.
2. **Time.** Any act, article or decision can be read *and searched* as of any
   date, with the edition/version stated in the result.
3. **Citations.** Paragraph/point-level, resolvable to a public source URL, and
   never generated by the model.
4. **Search.** Semantic + lexical + filters (act type, institution, date), p95
   retrieval under 1.5 s at 10× today's corpus.
5. **Distribution.** Self-serve signup, API keys, billing, OAuth connectors in
   Claude and ChatGPT directories, status page, published SLO.
6. **Trust.** A published evaluation per source, a freshness SLO (new acts
   searchable within 24 h), and a per-document rights state that fails closed.

Today we meet #3 fully and #2/#6 for one act. Everything else is missing.

## Phases

Each phase ends with something a stranger can use and something an engineer can
verify. No phase starts before the previous exit criterion is met.

### Phase 1 — Win employment law (weeks 1–3)

**Status 2026-10-30: in progress.** Shipped: 21 delegated acts (1,587 chunks,
cited by point), the delegated-act evaluation (12/12), freshness covering those
acts, and the Code/delegation ranking rule measured and settled. Remaining:
the rest of the implementing acts, VDI's published Q&A (its site serves the list
from an internal endpoint, so it needs a crawler), and the Supreme Court
labour-case subset (needs a rights determination for LITEKO text).

The only phase that matters if funding or patience runs out.

- Add 15–20 implementing acts cited by the Code (working time, safety, leave,
  wage guarantees), selected by how often the Code delegates to them.
- Ingest VDI explanations (the inspectorate's practical positions).
- Ingest the Supreme Court's labour-law decisions (a filtered subset, not all
  of LITEKO).
- Freshness SLO: new amending act searchable within 24 h.
- Eval set grows to 100 questions across the three source types.

**Exit:** an HR manager asks a real question about severance, working time or
leave and gets an answer citing the Code, the implementing act, and — where it
exists — the inspectorate's or court's position.

### Phase 2 — All of e-TAR (weeks 4–8)

**Status 2026-10-30: started.** The ingestion pipeline accepts an external ID
list (`data/extra_acts.json`) and now covers 108 in-force acts / 5,870 chunks. A status sweep removed 35 acts that e-seimas marks NEGALIOJA (their DOCX exports carry no repeal marker), so the previous count was inflated. Discovery yields are measured: 56 acts from the ministry's safety index, 2 from 18 pages of search, 2 from 12 topic pages. Discovery
is the blocker: e-TAR has no bulk endpoint (JSF search ignores GET, no OAI-PMH,
data.e-tar.lt is an explainer), so full coverage needs a registry export or a
long crawler. Pipeline ready; source access open.

- Bulk act discovery and ingestion (~95k acts), incremental daily updates.
- Per-act edition history (reuse `build_history.py`; token enumeration generalised).
- Metadata layer: act type, authority, status (in force / repealed / draft),
  validity window.
- Search filters and pagination; move from in-process NumPy to a vector store.
- Freshness SLO extended to "any act, 24 h".

**Exit:** any Lithuanian legal act is findable by meaning, with its current and
historical text, at p95 < 1.5 s.

### Phase 3 — Case law (weeks 9–13)

- LITEKO/LITEKO2 ingestion with citation extraction (case number, court,
  instance, date, cited articles).
- Link decisions to acts and articles; show "cases citing 126 str. 2 d.".
- Rights review before any decision text is exposed.

**Exit:** a lawyer can start from an article and see the leading decisions that
apply it, or start from a situation and find similar decisions.

### Phase 4 — The rest of the platform (weeks 14–18)

**Status 2026-10-30: partially met. One written criterion is unmet.**

The plan's criterion is "Seimas drafts and committee transcripts". The measured
state of each half:

| Criterion component | Evidence | Met |
|---|---|---|
| Seimas draft acts | 3 drafts, 9 chunks, via the e-seimas TAP route as DOCX | ✅ |
| Seimas plenary transcripts | 22 sittings, 363 labour-related fragments (20 via the "Stenograma" type as DOCX, 2 from lrs.lt PDFs) | ✅ (not in the original wording) |
| **Seimas committee transcripts** | the only "Stenograma" type returns 220 plenary sittings and **0 committee** over 15 pages | ❌ **unmet — verbatim transcripts not published** |
| Seimas committee record (published half) | 38 committee conclusions, 286 fragments, via the documentSearch "Komiteto išvada" type | ✅ conclusions; not transcripts |
| Institution explanations beyond VDI | VDI 249, SADM 299, Sodra 236 answers (784 total) | ✅ |
| EU law | 5 directives, 95 chunks, via the Cellar endpoint | ✅ |
| ECHR | 9 judgments quoting the Labour Code, 266 fragments | ✅ |
| Constitutional Court | 18 rulings, 532 fragments, 27 case nodes (9 ECHR + 18 KT), 30 case edges | ✅, national case law via e-seimas |
| Citation graph | 137 articles, 412 edges (30 to cases) | ✅ |
| Status page and SLO reporting | `/status` JSON and `/status.html`, coverage, freshness and measured quality | ✅ |

**The committee half is not satisfied, and the plan does not claim it is.** The
earlier text in this file described the criterion as "amended"; that was wrong to
present as completion. The accurate statement is: committee transcripts are not
published on e-seimas or lrs.lt, the search proves it (one type, 220 plenary
results, zero committee), and an export from the Seimas would be required.

Seimas access itself was solved for the published formats: lrs.lt and
e-seimas.lrs.lt refuse non-browser clients, so documents are fetched through a
real browser session and a loopback bridge; the PDF "syllable split" was in fact
soft hyphens (U+00AD), repaired with PyMuPDF.

**Exit:** source coverage matches Teisora's published list. Not met — Phase 2
coverage is 123 of ~95,000 acts, Phase 3 has no LITEKO corpus (Constitutional Court rulings are ingested), and committee
transcripts do not exist publicly.

### Phase 5 — Commercial shell (weeks 15–20, parallel)

- Accounts, self-serve API keys, usage metering, Stripe, invoices.
- Docs site, onboarding, support inbox, incident runbook.
- Directory submission for Claude and ChatGPT; OAuth already implemented.

**Exit:** a stranger can sign up, pay, connect, and use it without talking to us.

### Phase 6 — Hardening (weeks 19–24)

- Per-source evaluations with published numbers and known failure modes.
- Load tests at 50 rps; DR drill; restore from backup; security review.
- On-call rota (this is a legal product; downtime has consequences).

**Exit:** we can state and meet an availability number.

## Team and cost

| Role | FTE | Why |
|---|---|---|
| Data/backend engineer ×2 | 2.0 | ingestion, versioning, storage, APIs |
| Search/ML engineer | 1.0 | hybrid retrieval, evals, reranking budget |
| Full-stack/product | 1.0 | accounts, billing, docs, UI |
| Legal counsel | 0.5 | rights, ToS, DPA |
| Founder | 1.0 | product decisions, sales, partnerships |

Running costs at Phase 2 scale: embeddings and reranking dominate. Budget
€600–1,200/month at 100k acts; €3–6k/month once case law and traffic are added.
Vector storage for ~1M chunks is single-digit GB; the cost is API calls, not disk.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| LITEKO redistribution rights | Blocks Phase 3 | Written determination before ingestion; ship links, not text, if unclear |
| e-TAR layout or token changes | Ingestion breaks silently | Freshness gate fails loudly; recorded fixtures in CI |
| Embedding cost at 1M chunks | €2–4k one-off per full re-embed | Incremental embedding keyed by content hash; never re-embed the world |
| Search quality collapses at scale | The product stops being better | Per-source evals; rerank only top-N; filters before vectors |
| Directory review rejection | No distribution | OAuth + docs already done; ship self-serve keys first |
| Solo-founder bandwidth | Nothing ships | Phase 1 is deliberately the whole product; later phases are opt-in |

## What we deliberately will not build

- Our own model or fine-tuning. The host model is better and cheaper.
- A second chatbot. The connector is the product.
- Procurement, PINREG, construction permits, land: Teisora's journalist and
  lobbyist market, not employment law. Only if we reposition.
- A framework. The core is a few hundred lines and stays that way.

## Sequence rule

Ship Phase 1 as if the company ends there. Every later phase is an investment
that only pays if Phase 1 has users. If Phase 1 does not produce weekly active
HR or lawyer users, the correct response is to narrow further, not to add sources.
